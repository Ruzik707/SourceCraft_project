# Архитектура решения

## Схема

```
        сборщик (collector/)                     браузер
   обход каталога SourceCraft                       │
   Git-клон · API платформы · AppSec                │ /api/v1/...
                 │                                  ▼
                 ▼                          бэкенд (main.py, backend/)
        repo_health_report.csv  ──читает──►  витрина в памяти
        (одна строка на репозиторий)         │       │
                                             │       ├── методика (scoring/)
                                             │       ├── факты и статусы (facts.py)
                                             │       └── сборка ответов (presenter.py)
                                             │
                                    SQLite: сессии, история оценок, запуски анализа
                                             │
                        наружу: oauth.yandex.ru, login.yandex.ru, api.sourcecraft.tech
```

Три части независимы: сборщик не знает о бэкенде, бэкенд не импортирует сборщик (только
запускает команду), интерфейс знает лишь про свой API.

## Сборщик — `collector/`

Отдельный Python-проект со своими зависимостями. Обходит каталог платформы, для каждого
репозитория собирает шесть групп сигналов: документацию и лучшие практики, CI/CD,
Security через AppSec, активность по Git-истории, issues, состояние кода. Результат —
`output/<owner>__<name>/latest.json`, затем выгрузка в `repo_health_report.csv`.

Решения, важные для масштаба:

- **порционный обход** вместо полного: `--oldest-first` упорядочивает репозитории по
  времени последнего сбора, `--max-minutes` ограничивает длительность запуска;
- **параллельность** через `--concurrency` (по умолчанию 4);
- **реестр эндпоинтов** в `config/endpoints.yaml` с пометкой, что проверено на живом API;
- **запасной путь через CLI** `src api <path>`, когда REST отвечает ошибкой;
- **схема записи** в `schema/repo_health.schema.json` — контракт между сборщиком и бэкендом;
- **обновление одной строки** в `collect_one.py`: анализ по запросу не перестраивает весь
  CSV, а заменяет строку одного репозитория, подменяя файл целиком.

## Методика — `scoring/`

Считает Repo Health Score по шести категориям и формирует рекомендации. Ключевая
особенность: нормализация метрик идёт по min/max всей выборки, поэтому расчёт выполняется
разом по всему датасету — оценка одной строки в отрыве от выборки зависит от того, что
ещё попало в расчёт.

- `data_loader.py` — подготовка данных: заполнение пропусков, даты в «сколько дней назад»;
- `normalizer.py` — нормализация метрик, агрегация по категориям, веса (подобраны Optuna),
  итоговый Score; `compute_scores_frame` считает всю выборку, `calculate_health_score` —
  обёртка для одной записи;
- `recommender.py` — правила рекомендаций: проблема, важность, действие, эффект.

## Бэкенд — `backend/` и `main.py`

| Модуль | Ответственность |
| --- | --- |
| `store.py` | витрина: чтение выгрузки, прогон через методику, фильтры и сортировки рейтинга |
| `facts.py` | метрики, статусы категорий и причины «нет данных» из сырых колонок |
| `presenter.py` | сборка ответов по контракту: рейтинг, отчёт, рекомендации, сводка |
| `auth.py` | вход через Я ID, сессии, приём токена Яндекса как сессии |
| `sourcecraft.py` | клиент платформы: профиль, организации, репозитории пользователя |
| `analyses.py` | очередь анализа по запросу, стадии, запуск сборщика |
| `scheduler.py` | пересчёт по расписанию и запись истории оценок |
| `db.py` | SQLite: сессии, история, запуски |
| `api.py` | HTTP-слой |

**Витрина в памяти.** При старте сервис читает CSV (27 761 строка, 102 колонки), считает
оценки и держит результат в памяти: чтение занимает около пятнадцати секунд, расчёт —
около секунды. Все запросы рейтинга и отчётов обслуживаются без обращения к диску.
База нужна только для того, что должно пережить перезапуск.

**Разделение «баллы» и «факты».** Баллы приходят из методики, а метрики, статусы и
причины отсутствия данных собираются отдельно из сырых колонок. Благодаря этому
интерфейс показывает не только оценку, но и то, на чём она основана, а замена методики
не ломает объяснение.

**Анализ по запросу** ставится в очередь, выполняется в фоне и отдаёт стадии сбора.
Сборщик подключается командой `COLLECTOR_COMMAND`; если команда не задана, стадии сбора
помечаются пропущенными, а оценка пересчитывается по последнему снимку — интерфейс пишет
об этом прямо.

## Интерфейс — `frontend/`

React 18, TypeScript, Vite, React Router, TanStack Query. Графики — собственные
SVG-компоненты, без графических библиотек: меньше вес и полный контроль над состоянием
«нет данных». Стили — CSS с переменными, светлая и тёмная темы, визуальный язык
повторяет SourceCraft.

```
компоненты → хуки (api/hooks.ts) → фасад (api/index.ts) ─┬→ HTTP-клиент (client.ts)
                                                          └→ снимок данных (mock.ts)
```

Фасад выбирает источник по `VITE_DATA_SOURCE`, поэтому интерфейс работает и без бэкенда —
на снимке в `public/mock`. Состояние фильтров рейтинга живёт в адресной строке: ссылкой
можно поделиться.

Отсутствие данных обрабатывается на всех экранах: в таблице это пунктирная засечка «н/д»,
в радаре — штриховой контур, в карточке категории — причина и пометка «вес 20% → 0%».

Отчёт выгружается в Markdown (собирается в браузере из того же объекта, что показан на
экране) и в PDF (печать страницы; печатные стили принудительно возвращают светлую
палитру, убирают навигацию и дописывают адреса ссылок).

## Потоки данных

**Публичный рейтинг.** Выгрузка → витрина в памяти → `GET /repos` с фильтрами и
пагинацией → таблица рейтинга. Сети при этом не требуется.

**Страница анализа.** Витрина + сырые колонки → `presenter` собирает категории с
метриками, рекомендации и сведения о полноте данных → `GET /repos/{owner}/{name}`.

**Личный кабинет.** Вход через Я ID → сессия в базе → `GET /me/repos` идёт в платформу от
имени пользователя: профиль `/user`, организации `/me/orgs`, репозитории
`/orgs/{slug}/repos`. Закрытые репозитории видны только владельцу.

**Анализ по запросу.** `POST /analyses` → очередь → сборщик обновляет строку в CSV →
витрина пересобирается → отчёт и точка в истории.

**Периодический пересчёт.** Планировщик по cron пересобирает витрину и пишет историю
оценок; сборщик независимо обновляет выгрузку порциями.

## Масштабирование

| Узкое место | Решение |
| --- | --- |
| Рост числа репозиториев | сбор порциями с приоритетом старых записей, параллельные воркеры |
| Крупные репозитории | поверхностное клонирование с ограничением истории, таймаут на репозиторий |
| Расчёт витрины | векторные операции pandas: 27 761 репозиторий за секунду |
| Нагрузка на рейтинг | пагинация и фильтры на стороне API, витрина в памяти |
| Отдача интерфейса | статика за nginx, масштабируется репликами |
| Недоступность источника | ошибка становится статусом «нет данных» у категории, прогон не падает |

## Безопасность данных

Закрытые репозитории исключены из рейтинга, статистики и списка языков; отчёт по такому
репозиторию отдаётся только владельцу, постороннему возвращается 404, чтобы не
раскрывать сам факт существования. Токены платформы хранятся в сессии и удаляются вместе
с ней. Исходный код не хранится: сборщик клонирует репозиторий во временный каталог и
удаляет его после анализа.

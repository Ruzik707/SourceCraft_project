# Методика расчёта Repo Health Score

Краткое описание того, как из сырых сигналов получается оценка от 0 до 100. Код —
в `scoring/`: подготовка данных в `data_loader.py`, расчёт в `normalizer.py`, правила
рекомендаций в `recommender.py`.

## Шесть категорий и веса

| Категория | Вес | Что в неё входит |
| --- | --- | --- |
| Состояние кода | 29,8% | плотность TODO/FIXME/HACK, давность пометок, размер файлов, объём кода |
| Security | 19,8% | результаты AppSec: группы дефектов по критичности и статусу, возраст открытых, наличие политики безопасности |
| Issues | 19,1% | открытые и закрытые задачи, зависшие и без ответа, время до первого ответа и до закрытия |
| Активность | 10,8% | коммиты за 30/90/365 дней, дата последней активности, контрибьюторы, bus factor, ветки, теги, релизы, merge request |
| CI/CD | 10,2% | наличие конфигурации, стадии сборки, тестов, линта и деплоя, статусы и длительность прогонов, защита веток |
| Документация | 10,0% | README и его длина, разделы, лицензия, CONTRIBUTING, CODE_OF_CONDUCT, CHANGELOG, каталог документации, шаблоны issue и PR |

Веса подобраны на исторической выборке (Optuna), а не назначены вручную. Текущая версия
методики помечается в отчётах как `scoring-optuna-1.0`.

## Как считается оценка категории

1. **Нормализация метрик.** Каждая числовая метрика приводится к шкале 0–100 по
   минимуму и максимуму всей выборки. Для величин с тяжёлым хвостом — строки кода,
   размер README, число коммитов, лайки — сначала берётся логарифм, иначе несколько
   гигантских репозиториев сожмут всю остальную шкалу.
2. **Направление учитывается.** Для одних метрик больше — лучше (коммиты,
   контрибьюторы, закрытые задачи), для других наоборот (зависшие задачи, возраст
   открытых дефектов, размер самого большого файла, дни с последнего коммита).
3. **Логические признаки** превращаются в 0 или 100: есть README — 100, нет — 0.
4. **Особые правила** там, где шкала известна заранее: доля успешных прогонов CI берётся
   как есть, bus factor считается как «единица минус доля главного автора», критичность
   дефектов отображается вручную (CRITICAL и HIGH — 0, MEDIUM — 60, LOW — 80).
5. **Оценка категории** — среднее её нормализованных метрик.

## Как считается итог

```
Score = Σ (оценка категории × вес категории) ÷ Σ (веса активных категорий)
```

Знаменатель пересчитывается для каждого репозитория: если категория неактивна, её вес
не участвует ни в числителе, ни в знаменателе. Сумма вкладов всегда сходится с итогом —
эта таблица показана пользователю на странице анализа.

Буквенная оценка: A — от 85, B — от 70, C — от 55, D — от 40, ниже — E.

Рядом с оценкой всегда показана **полнота данных**: доля веса методики, подтверждённая
фактическими данными.

## Обработка отсутствующих данных

Отсутствие данных не считается плохим результатом:

- **пропущенное значение метрики** заменяется нейтральной оценкой 50, а не нулём;
- **категория, которую сборщик пометил как недоступную**, исключается из расчёта:
  сейчас это работает для Security и CI/CD, у которых платформа отвечает отказом без
  прав на репозиторий;
- **в интерфейсе** такие категории видны отдельным статусом: «нет данных» с причиной,
  «не применимо» (например, трекер задач не используется) или «собрано частично» с
  указанием доли доступных сигналов.

Известное ограничение: документация, активность, issues и состояние кода участвуют в
расчёте всегда, даже когда рабочую копию получить не удалось, — они считаются по
нейтральным значениям. Интерфейс это честно помечает; вопрос вынесен в
[`limitations.md`](./limitations.md).

## Рекомендации

Формируются правилами над собранными фактами: у каждого правила есть условие
срабатывания, формулировка проблемы, объяснение важности, конкретное действие и
ожидаемый эффект. Рекомендации сортируются по приоритету — критический, высокий,
средний, низкий. Текстов, сгенерированных языковой моделью, в отчёте нет: одни и те же
данные всегда дают один и тот же набор рекомендаций.

## Устойчивость

- **Лайки не входят в Score** — они показаны отдельной колонкой рейтинга, чтобы
  популярность не подменяла здоровье проекта.
- **Метрики нормализованы по размеру проекта**: плотность пометок на тысячу строк, доли
  зависших и неотвеченных задач. Крупный репозиторий не штрафуется за объём.
- **Ни один сигнал не решает всё**: вклад отдельной метрики ограничен весом её
  категории, делённым на число метрик внутри неё.
- **Полнота данных видна**: репозиторий с одной собранной категорией нельзя выдать за
  проверенный по всем шести, а в рейтинге есть фильтр по полноте.

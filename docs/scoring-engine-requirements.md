# ТЗ для Scoring Engine: что нужно веб-интерфейсу

Документ для роли «методика Repo Health Score». Формат ответов API — в
[`api-contract.md`](./api-contract.md), текущее состояние сборки — в
[`status-and-integration.md`](./status-and-integration.md).

## Коротко: что сделать, если алгоритм уже написан

Методику заново придумывать не нужно — нужно, чтобы её вывод давал вебу то, из чего
строится объяснение оценки. По убыванию важности:

1. **Отдавать `null` вместо `0`** для категорий, по которым не было данных, и рядом
   `status`: `ok` / `partial` / `no_data` / `not_applicable`.
2. **Писать причину** в `no_data_reason` одной фразой: «AppSec вернул 403»,
   «репозиторий не склонировался».
3. **Два веса** на категорию: `weight` (в методике) и `effective_weight` (после исключения
   пустых категорий). Сумма `score × effective_weight` обязана сходиться с итогом —
   интерфейс показывает эту таблицу пользователю.
4. **Метрики**, на которых основан балл: значение, готовая строка для показа, источник.
5. **По 2–3 формулировки** сильных и слабых сторон на категорию.
6. **`formula_version` и `analyzed_at`**, плюс строка истории на каждый пересчёт.
7. **Проверить алгоритм на контрольных репозиториях** (раздел B3) и записать результат.

Пункты 1–5 сейчас закрывает бэкенд: он берёт баллы из `scoring/`, а факты, статусы и
причины собирает из сырой выгрузки (`backend/facts.py`). Если методика начнёт отдавать их
сама — бэкенд будет просто их пробрасывать.

## Часть A. Что показывает интерфейс

### A1. Минимум
`total_health_score`, шесть `score_*`, `formula_version`, `analyzed_at`. Ноль и «нет
данных» — разные значения: `0` окрасит категорию в красное там, где данных просто не было.

### A2. Для объяснимости
`status`, `weight`, `effective_weight`, `signal_coverage`, `no_data_reason`, `metrics[]`,
`strengths[]`, `weaknesses[]`. Без них останутся пустыми раскрытие категории до фактов,
блок полноты данных и сильные/слабые стороны — это критерии «объяснимость оценки» (до 5
баллов) и «связь рекомендаций с фактами» (до 5 баллов).

### A3. Рекомендации
Сейчас движок отдаёт `problem`, `importance`, `action`, `impact` — этого хватает, интерфейс
показывает текст эффекта. Чтобы вместо текста появился числовой прирост, нужен
`expected_gain`: сколько баллов вернёт исправление внутри категории, умноженные на её
эффективный вес.

## Часть B. Требования к методике

### B1. Обоснование метрик и порогов
Для каждой метрики: что измеряем, из какого поля сборщика, почему это сигнал здоровья,
откуда порог. *Приёмка:* по описанию посторонний человек повторит расчёт вручную.

### B2. Веса и нормализация
Описать веса шести категорий, правило перенормировки при отсутствии данных и приведение
метрик к сопоставимому виду. Сейчас веса подобраны Optuna (0.198 / 0.298 / 0.191 / 0.108 /
0.100 / 0.102) — нужно объяснить, на какой выборке и по какому критерию.
*Приёмка:* расчёт воспроизводится на тех же данных (2 балла по рубрике).

### B3. Проверка на контрольных сценариях

| Сценарий | Репозиторий | Что проверяем |
| --- | --- | --- |
| Активный крупный проект без CI-конфига | `userver/userver` | активность высокая, CI низкий |
| Зрелый проект с документацией | `annetutil/annet` | 39 контрибьюторов, лицензия, CONTRIBUTING |
| Рабочая копия не получена | `gravity-ui/aikit` | четыре категории без данных |
| Клон упал с ошибкой пути | `0x4b4c494d/awg` | корректная деградация |
| Крошечный репозиторий без README | `08111987/tetris` | малый объём не даёт ложно высокий балл |

*Приёмка:* таблица «репозиторий → что изменили → как изменился Score» по шести категориям.

### B4. Устойчивость к перекосам
Лайки не входят в Score; серия пустых коммитов почти не двигает активность; `SECURITY.md`
не поднимает Security; низкое покрытие данными не даёт преимущества.

### B4-бис. Открытый вопрос: категории без собранных данных

Сейчас из знаменателя исключаются только `security` и `cicd`, когда сборщик пометил их как
`unavailable`. Флаги `is_issues_active`, `is_activity_active`, `is_docs_active`,
`is_health_active` в `scoring/normalizer.py` заданы константой 1, поэтому при неудачном
клоне документация, активность и состояние кода всё равно попадают в расчёт — по
нейтральным значениям нормализации.

Пример: у `gravity-ui/aikit` клон не выполнился, но документация получила 8/100, а
активность 28/100. Это не измеренное качество, а следствие нейтральных значений.

Бэкенд здесь ничего не меняет — отдаёт ровно то, что посчитала методика, а интерфейс
помечает такие категории как «собрано частично» с пояснением. Решение за автором методики:

1. расширить маску активных категорий на все шесть — тогда категория без данных
   исключается так же, как security и cicd;
2. оставить как есть и обосновать, почему нейтральное значение корректнее исключения.

Первый вариант ближе к требованию ТЗ «отсутствие данных нельзя автоматически трактовать
как плохой результат»: сейчас оно выполняется для двух категорий из шести.

### B5. Расчёт внутри сервиса
Пересчёт по расписанию для всех открытых репозиториев, фиксация времени и статуса,
устойчивость к отказу отдельных источников, запуск по требованию из кабинета.

### B6. Витрина и история
`score_*`, `total_health_score`, `formula_version`, `analyzed_at` плюс строка на каждый
пересчёт — из неё интерфейс рисует динамику Score.

## Часть C. Что важно знать про данные

Снимок на 20–21 сентября 2026 года, 27 761 репозиторий:

- **AppSec доступен ровно для 1 репозитория**, история CI — для 2: платформа отвечает 403
  анонимному сборщику. «Нет данных» — основной сценарий, а не крайний случай.
- README есть у 16 482 репозиториев, лицензия — у 2 237.
- Лайки ненулевые у 1 264 — как сигнал почти не работает.

## Часть D. Где что лежит

| Что | Где |
| --- | --- |
| Расчёт категорий | `scoring/normalizer.py`, функции нормализации и агрегации |
| Веса и версия методики | `BEST_WEIGHTS`, `FORMULA_VERSION` там же |
| Маска активных категорий | `default_active_mask` там же |
| Батч-расчёт по всей выгрузке | `compute_scores_frame` там же |
| Подготовка данных | `scoring/data_loader.py` |
| Правила рекомендаций | `scoring/recommender.py` |
| Витрина в памяти | `backend/store.py` |
| Факты, статусы, причины | `backend/facts.py` |
| Сборка ответов API | `backend/presenter.py` |

Нормализация считает min/max по всей выборке, поэтому расчёт идёт разом по всему датасету:
оценка одной строки в отрыве от выборки зависит от того, что ещё попало в расчёт.

## Часть E. Чек-лист готовности

- [ ] Расчёт воспроизводится вручную по описанию на одном репозитории
- [ ] Категория без данных приходит как `null` со `status` и причиной, а не как `0`
- [ ] Сумма `score × effective_weight` сходится с `total_health_score`
- [ ] Контрольные сценарии покрывают шесть категорий и задокументированы
- [ ] Решён вопрос B4-бис про категории без собранных данных
- [ ] Описано, какие действия не позволяют искусственно поднять Score
- [ ] Пересчёт выполняется по расписанию и записывает время и статус

# Что сделано, что на моках и что нужно подключить

Документ для команды: текущее состояние веб-интерфейса, список заглушек и порядок
перехода с демо-данных на боевой бэкенд.

## 1. Что закрывает интерфейс по критериям оценки

| Критерий | Что сделано во фронтенде | Чего не хватает |
| --- | --- | --- |
| **Рабочий продукт — 35** | Все обязательные сценарии работают сквозняком: рейтинг → страница анализа → выгрузка отчёта; вход через Я ID → выбор своего репозитория → запуск анализа → результат → повторный запуск с разницей Score. Воспроизводимый запуск: `npm ci && npm run build`, Dockerfile + nginx. | Сценарии ходят в мок-транспорт; нужны боевые эндпоинты (раздел 3) |
| **Качество метрик и аналитики — 30** | Объяснимость: таблица «как получилась оценка», где сумма вкладов равна Score; раскрытие категории до метрик с источником (Git-клон, API платформы, AppSec); рекомендации с проблемой, обоснованием, фактами, действием и ожидаемым приростом в баллах; отдельный блок полноты данных и ошибок сбора. | Сама методика — зона Scoring Engine. ## 2. Что сейчас заглушено моками

Включается флагом `VITE_DATA_SOURCE=mock` в `frontend/.env`. Всё, что ниже, живёт в
`frontend/public/mock/` и `frontend/src/api/mock.ts`.

| Подсистема | Чем заглушено | Что придёт вместо |
| --- | --- | --- |
| Рейтинг репозиториев | `repos.json` — 1500 репозиториев из снимка `repo_health_report.csv` (20–21 сентября 2026) | `GET /repos` с пагинацией и фильтрами на стороне API |
| Отчёт по репозиторию | `reports/<owner>__<name>.json`, по файлу на проект | `GET /repos/{owner}/{name}` |
| **Значения Score** | Демонстрационная формула в `tools/build_mock_data.py`, помечена как `formula_version: demo-0.3.0` | Витрина Scoring Engine: `score_*` и `total_health_score` |
| Языки и сводка платформы | `languages.json`, `stats.json` | `GET /languages`, `GET /stats` |
| Вход через Я ID | Редирект на `/auth/callback` с фиктивным токеном; профиль из `me.json` | `GET /auth/yandex/login` → согласие Яндекса → callback с настоящим токеном |
| Список своих репозиториев | 6 репозиториев из `me.json` | `GET /me/repos` от имени пользователя |
| Запуск анализа | Таймеры в `mock.ts`: шесть стадий за ~6 секунд, стадия AppSec помечается пропущенной | `POST /analyses` + опрос `GET /analyses/{id}` |
| История Score | Одна точка — дата последнего сбора | Накапливается бэкендом при каждом пересчёте |
| PDF с сервера, SVG-бейдж | Пунктов нет: PDF печатается браузером, бейдж только копируется как Markdown | `GET /repos/.../report.pdf`, `GET /badge/{owner}/{name}.svg` |

Что **не** заглушено и работает по-настоящему уже сейчас: вся логика интерфейса,
выгрузка Markdown (собирается в браузере из объекта отчёта), печать в PDF, фильтры,
сортировки, сравнение проектов, переключение тем, обработка ошибок и пустых данных.

## 3. Порядок подключения боевого бэкенда

Контракт — [`api-contract.md`](./api-contract.md) и [`openapi.yaml`](./openapi.yaml).
Переключение идёт по шагам: каждый шаг оживляет свой кусок интерфейса, остальное
продолжает работать.

**Шаг 1. Публичная часть — сделано.** `GET /repos`, `GET /repos/{owner}/{name}`,
`GET /languages`, `GET /stats` реализованы в `backend/api.py` поверх витрины, которую
собирает `backend/store.py` из выгрузки сборщика и методики `scoring/`. Рейтинг и страницы
анализа работают на боевых данных: 27 761 репозиторий, оценено 26 578.

**Шаг 2. Авторизация — сделано.** `GET /auth/yandex/login` уводит на согласие Я ID,
`/auth/yandex/callback` меняет код на токен и заводит сессию, работают `GET /me`,
`GET /me/repos` и `POST /me/sourcecraft-token`. Осталось завести приложение на
oauth.yandex.ru и задать `YANDEX_CLIENT_ID`/`YANDEX_CLIENT_SECRET`: пока их нет, вход идёт
в демо-режиме.

**Шаг 3. Анализ по запросу — сделано.** `POST /analyses` ставит задачу в очередь,
`GET /analyses/{id}` отдаёт статус, прогресс и стадии. Запуски и история оценок хранятся
в базе. Осталось подключить сборщик: пока `COLLECTOR_COMMAND` не задана, стадии сбора
помечаются пропущенными, а оценка пересчитывается по последнему снимку — интерфейс пишет
об этом прямо.

**Шаг 4. Необязательное.** `GET /repos/.../report.pdf` (серверный PDF) и
`GET /badge/{owner}/{name}.svg` (бейдж для README) — интерфейс подхватит их
автоматически, дополнительный пункт появится в меню выгрузки.

**Переключение фронта:**

```bash
# frontend/.env
VITE_DATA_SOURCE=api
VITE_API_BASE_URL=/api/v1
VITE_PROXY_TARGET=http://localhost:8000   # только для npm run dev
```

Для стенда:

```bash
docker build -t repo-health-frontend --build-arg VITE_DATA_SOURCE=api frontend
```

В `frontend/nginx.conf` поправить адрес апстрима (`proxy_pass http://backend:8000`).
Правок в коде интерфейса не требуется: источник данных выбирает фасад
`src/api/index.ts`, компоненты о нём не знают.

## 4. Как убедиться, что фронт переключился

1. Исчезает жёлтый баннер «Демо-режим», в сайдбаре бейдж меняется на «боевые данные».
2. В шапке отчёта `методика demo-0.3.0` заменяется на версию витрины.
3. Кнопка «Пересчитать» в кабинете ставит настоящую задачу: в списке стадий видно,
   какие источники ответили, а какие вернули отказ.
4. Выгруженный Markdown содержит те же цифры, что и веб-страница (значения приходят
   готовыми строками из поля `display`).

## 5. Что мешает закрыть полностью

- **AppSec недоступен анонимно.** В снимке данных результаты AppSec есть ровно у одного
  репозитория из 27 761, история CI — у двух. Пока сборщик ходит без прав, категории
  Security и CI/CD у большинства проектов останутся со статусом «нет данных». Это
  обработано в интерфейсе, но для демонстрации полноценного Security-блока нужен хотя бы
  один репозиторий, где команда сама включила сканирование.
- **Полнота данных влияет на сопоставимость.** Репозиторий, у которого собрана одна
  категория, формально может получить высокий Score. В рейтинге это закрыто фильтром
  «полнота не ниже 50%», но правильное решение — учитывать полноту в самой методике.
- **История Score** появится только после второго планового пересчёта на бэкенде.

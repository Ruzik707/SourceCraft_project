# Польза решения для пользователей и платформы

## Проблема, измеренная по самому каталогу

Сервис проанализировал **27 761 открытый репозиторий SourceCraft**. Картина, которую
раньше никто не видел целиком:

| Признак зрелости | Доля каталога |
| --- | --- |
| Есть README | 59% (16 482) |
| **Есть лицензия** | **8% (2 237)** |
| Настроен CI | 23% (6 389) |
| Нет коммитов больше 90 дней | 65% (18 037) |
| Нет коммитов больше года | 7% (2 008) |
| **Весь код за год написал один автор** | **55% (15 155)** |

Медианный Repo Health Score — 52 из 100.

Каждая строка здесь — конкретная проблема пользователя платформы. Отсутствие лицензии
у 92% проектов означает, что их нельзя легально переиспользовать. Один автор у 55%
репозиториев — это проекты, которые остановятся, если человек уйдёт. Ответы на такие
вопросы сегодня разбросаны между Git-историей, README, пайплайнами, результатами
сканирования, issues и merge request: чтобы оценить один проект, нужно вручную свести
шесть источников, а каталог растёт.

## Что получает каждая аудитория

**Разработчик и maintainer** видит не «оценку», а список действий. Каждая рекомендация
содержит проблему, обоснование важности, факты, на которых сделан вывод, конкретное
действие и ожидаемый эффект на Score. Например: «конфигурация CI не найдена → добавьте
`.sourcecraft/ci.yaml` со стадиями сборки, тестов и линта → +10,4 балла». После
исправлений анализ запускается повторно и показывает разницу — работа над качеством
становится измеримой.

**Тимлид и технический руководитель** получает срез по своим проектам в одном месте:
где просел CI, где копится технический долг, где задачи висят без ответа. Bus factor
считается по распределению коммитов, а не на глаз, — видно, какие проекты держатся на
одном человеке.

**CTO и владелец продукта** может сравнить проекты между собой и объяснить решение
цифрами: страница сравнения ставит до четырёх репозиториев рядом по всем шести
категориям и по полноте данных.

**Команда, выбирающая открытый компонент**, за минуту отвечает на вопросы, на которые
раньше уходил час: живой ли проект, есть ли лицензия, проходят ли тесты, как быстро
отвечают на issues, не зависит ли он от одного разработчика. Рейтинг сортируется по
здоровью, а не по популярности: лайки вынесены отдельной колонкой и в Score не входят.

**Владелец платформы** впервые получает измеримую картину качества каталога и может
отслеживать её в динамике: история оценок пишется при каждом пересчёте.

## Что это даёт платформе SourceCraft

**Аналитический слой, которого не было.** Платформа хранит данные — Git-историю,
пайплайны, результаты AppSec, issues, — но не превращает их в ответ на вопрос «что с
этим проектом». Сервис делает это регулярно и для всего каталога сразу.

**Понятный стимул пользоваться возможностями платформы.** Из 27 761 репозитория данные
AppSec доступны у одного, история пайплайнов — у двух. Когда проект видит в отчёте
«Security: нет данных — категория исключена из расчёта», у владельца появляется повод
включить сканирование. То же с CI: 77% репозиториев не имеют конфигурации, и сервис
прямо показывает, сколько баллов это стоит.

**Навигация по каталогу.** Рейтинг с фильтрами по языку, полноте данных, наличию CI и
статусу Security — это способ находить живые проекты среди 27 тысяч, а не только те,
что кто-то залайкал.

**Обратная связь о самой платформе.** Ошибки сбора не прячутся: в отчёте видно, какие
ручки API отвечают отказом и каким данным нельзя доверять. Это готовый список того,
что стоит починить или задокументировать — например, в ходе работы выяснилось, что
`/me/repos` возвращает не все репозитории пользователя, а личные проекты приходят
только через организации.

**Публичный сигнал качества.** Badge для README и публичная страница отчёта дают
проектам то же, что даёт бейдж сборки: видимый повод поддерживать порядок.

## Почему решение устроено именно так

**Оценка объяснима до факта.** Сумма вкладов категорий сходится с итоговым Score, и эта
таблица показана пользователю. Любую цифру можно развернуть до метрики и источника —
Git-клон, API платформы, AppSec. Без этого оценка остаётся непрозрачной, и ей не верят.

**Отсутствие данных — это статус, а не ноль.** Категория без данных исключается из
расчёта и не портит оценку; в интерфейсе она выглядит иначе, чем плохой результат, и
сопровождается причиной. Рядом всегда показана полнота данных — какая доля веса
методики подтверждена фактами. Это принципиально для каталога, где AppSec доступен
меньше чем у процента проектов.

**Рейтинг нельзя накрутить популярностью.** Лайки не входят в Score. Метрики
нормализованы по размеру проекта, поэтому крупный репозиторий не штрафуется за объём, а
мелкий не выигрывает за счёт малого числа TODO. Ни один отдельный сигнал не может
изменить итог больше, чем на вес своей категории.

**Решение рассчитано на рост каталога.** Сбор идёт порциями с приоритетом самых старых
записей и параллельными воркерами; расчёт витрины векторный и занимает около секунды на
27 тысяч репозиториев; интерфейс — статика, масштабируется репликами.

## Как измерить эффект

Сервис фиксирует историю оценок, поэтому польза проверяется по самим данным:

- доля репозиториев с лицензией и README — сейчас 8% и 59%;
- доля проектов с настроенным CI — сейчас 23%;
- медианный Repo Health Score каталога — сейчас 52;
- доля проектов, где данные AppSec доступны, — сейчас меньше процента;
- динамика Score у репозиториев, владельцы которых открывали отчёт.

Это и есть критерий успеха: если через месяц после запуска доля лицензий и настроенного
CI растёт, а медианный Score поднимается, сервис работает.

## Границы применимости

Оценка описывает инженерную гигиену, а не ценность проекта: учебный репозиторий с
README, лицензией и CI получит больше баллов, чем сложная библиотека без документации.
Score стоит читать как «насколько с проектом удобно и безопасно работать другим», а не
как «насколько он хорош». Полный список ограничений — в [`limitations.md`](./limitations.md).
